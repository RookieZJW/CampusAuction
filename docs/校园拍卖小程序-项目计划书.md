## 0. 一页速览

**做什么**：一个面向校园场景的 C2C 在线拍卖平台。学生把闲置物品（教材、数码、自行车、手办）挂上拍卖，设置起拍价、加价幅度与截止时间，其他学生在倒计时内公开竞价，价高者得，线下当面交割。

**为什么这么选题有价值**：校园二手交易的真实痛点是**定价难、议价成本高、信息不对称**。跳蚤市场靠喊价、闲鱼靠私聊砍价，双方都不掌握"合理价格"。拍卖机制让价格由市场发现，同时用时间压力提升成交效率——毕业季、换季清仓场景下尤其成立。

**三个创新点**（论文可用，答辩可讲）：

1. **防狙击延时竞价机制（Anti-sniping）**：截止前 5 分钟内有新出价，自动延长 2 分钟，最多延长 3 次。解决"最后 1 秒压哨出价导致其他人来不及反应"的公平性问题。
2. **高并发出价的一致性保障**：Redis Lua 原子脚本做前置拦截 + 数据库乐观锁（version）做最终兜底的双层方案，并用 JMeter 压测验证。
3. **AI 辅助定价**：基于同类历史成交样本统计 + 大模型推理，为卖家生成起拍价区间建议与商品卖点描述，降低"定价难"门槛。

**系统边界（必须在论文里写清楚的取舍）**：

- 平台**不触碰真实资金**。采用虚拟保证金（注册赠 100 币，参拍冻结 10 币）+ 线下当面交割。
- 理由：个人主体小程序无法开通微信支付；"拍卖"属微信限制类目，需《拍卖经营批准证书》。毕设以开发版/体验版演示，不提审上线。
- 论文中保留"支付模块设计"章节，说明生产环境接入微信支付的完整流程（下单→签名→回调→对账），但代码层仅预留接口。**这是加分项，不是减分项。**

## 2. 技术选型与论证

### 2.1 两条路线对比（论文"相关技术"章节可直接引用）

| 维度 | 方案 A：Spring Boot 自建 | 方案 B：微信云开发 |
|---|---|---|
| 开发工作量 | 大（三层架构 + 部署联调） | 小（云函数直连 DB） |
| 部署成本 | 云服务器 + 备案域名 + HTTPS | 零（免备案、有免费额度） |
| 论文技术深度 | 高 | 中 |
| 答辩可讲点 | 多（缓存、锁、并发、定时任务） | 少 |
| 高并发竞价支撑 | 强（Redis + 乐观锁） | 弱（事务能力受限） |
| 部署风险 | 域名备案可能卡 2-3 周 | 几乎无 |

**选型结论：方案 A。**

理由三条：
1. 题目要求"设计与实现"，评委会重点看系统设计章节。云开发架构层次薄，设计章节难以展开。
2. 拍卖系统的核心技术难点是**并发竞价的一致性**，这正是 Spring Boot + Redis 的强项；云开发在此处是短板。
3. 已有 Spring Boot 3 + Redis + Resilience4j 实践基础，迁移成本低。

**部署风险规避**：毕设演示统一使用**开发版/体验版 + 开发者工具"不校验合法域名"**，真机预览同样生效，无需 ICP 备案。论文中补充"生产环境需完成域名备案与 HTTPS 配置"说明即可。若导师要求必须有线上地址，再走备案（预留 2 周缓冲）。

### 3.3 数据库设计（14 张表）

**设计要点（论文可展开）**：

- **物品与拍卖解耦**：`t_item` 存"东西是什么"，`t_auction` 存"怎么拍"。好处是同一件物品流拍后可以调价重新上拍，不必重复录信息；也便于扩展"一口价"模式。这是架构上的加分设计。
- **状态机**：`t_auction.status` 取值 `PENDING(待审) → READY(待开始) → ONGOING(进行中) → FINISHED(已成交) / FAILED(流拍) / CANCELLED(已取消)`，所有状态流转在 Service 层统一校验，禁止直接 UPDATE。
- **幂等**：`t_order.auction_id` 建唯一索引，结算任务重复执行时插入会被数据库拦下，从根上防重复建单。
- **金额单位**：一律用 `int`（分）存储，禁用 float/double，避免精度问题。这条答辩必问。

### 3.4 核心机制设计

#### 3.4.1 出价流程与并发一致性（本项目最核心的技术点）

**问题**：A、B 同时出价 100 和 105，若都用"读当前价 → 判断 → 写新价"，则 A 可能读到 95 判定合法，B 读到 95 判定合法，最终 100 覆盖 105，造成错价。

**双层方案**：

```
第一层：Redis Lua 原子预校验（拦掉 90% 无效请求）
  KEYS[1] = auction:price:{auctionId}
  ARGV[1] = 出价金额, ARGV[2] = 加价幅度, ARGV[3] = 出价用户ID

  if 出价 < 当前价 + 加价幅度 then return -1        -- 价格不合法
  if 出价用户 == 当前领先者 then return -2          -- 禁止自己超自己
  SET auction:price:{id} 出价
  return 1

  Lua 脚本在 Redis 单线程内原子执行，天然串行化。

第二层：MySQL 乐观锁兜底（保证最终一致）
  UPDATE t_auction
     SET current_price = #{price},
         current_winner_id = #{userId},
         bid_count = bid_count + 1,
         version = version + 1
   WHERE id = #{auctionId}
     AND version = #{oldVersion}
     AND status = 'ONGOING'
     AND current_price < #{price}

  影响行数 = 0 → 出价失败，返回"当前价已变动，请重新出价"
```

**为什么两层都要**：Redis 挡掉绝大多数无效请求（性能），数据库乐观锁保证即使 Redis 被击穿或重启也不会错价（正确性）。论文里这叫"性能与一致性的分层权衡"。

**实时刷新**：小程序端不做 WebSocket（成本和复杂度不划算），改用 **3 秒轮询 + 页面级 diff**：只请求 `{currentPrice, bidCount, endTime, topBidder}` 四个字段，用 `setData` 局部路径更新。这样既实时又不卡。

#### 3.4.2 防狙击延时机制

```
出价成功后判定：
  if (endTime - now <= 5分钟) && (extendCount < 3) {
      endTime = now + 2分钟;
      extendCount++;
      记录延时日志；
      推送"本场拍卖已延长"通知给所有出价者；
  }
```

设计理由：不加次数上限会出现"永远延不完"的拍卖（两个人反复压哨）。上限 3 次是业界常见做法（类似 eBay 的延时规则）。论文里可讨论这个参数的取值权衡。

#### 3.4.3 保证金与信用分

| 机制 | 规则 | 目的 |
|---|---|---|
| 虚拟余额 | 注册赠 100 币；参拍冻结 10 币；未中标自动解冻 | 提高恶意出价成本 |
| 违约扣分 | 中标后 48h 未完成交割，扣 10 信用分 + 扣保证金 | 抑制"拍了不买" |
| 信用分 | 初始 100；违约 -10、被举报核实 -20、正常成交 +2 | 低于 60 限制出价 |
| 出价门槛 | 信用分 < 60 或余额 < 保证金 → 禁止出价 | 前置拦截 |

> 这套机制在论文里是很好的"业务设计"素材——它体现了对真实交易风险的思考，比纯 CRUD 有说服力。

#### 3.4.4 到期结算（幂等 + 可靠）

```
Spring @Scheduled(fixedDelay = 30s)
  → 查 status='ONGOING' AND end_time <= now() 的场次（加 Redis 分布式锁防多实例重复执行）
  → 逐条处理：
     有出价：
        UPDATE status='FINISHED'
        INSERT t_order（auction_id 唯一索引保证幂等）
        解冻中标者保证金 → 转为待支付
        解冻其他竞拍者保证金
        发通知
     无出价：status='FAILED'（流拍）
```

生产环境更优雅的方案是 Redis ZSet 延时队列（score = end_time，定时 pop 过期成员），论文"展望"章节可提，毕设用定时扫描足够。

#### 3.4.5 AI 辅助定价（创新点三）

**输入**：标题、描述、分类、成色、图片
**处理**：
1. 服务端查同分类最近 20 条成交记录，算出 `min / median / max` 三个统计值
2. 组装 prompt 调大模型，要求返回严格 JSON：`{ suggestMin, suggestMax, sellingPoints: [3条], riskTip }`
3. 结果落库 `t_item.ai_suggest_min/max`，前端展示"AI 建议起拍价 ¥XX–¥YY"

**关键安全点**：API Key 只放服务端环境变量（`application.yml` 读环境变量，不硬编码）。小程序端绝不出现 Key——答辩老师如果懂技术，一定会问这个。

**降级策略**：AI 接口超时/失败时，直接返回统计值区间（`median * 0.8 ~ median * 1.2`），保证发布流程不中断。这是工程思维的体现，答辩加分。

### B.2 关键设计调整

**① 热点字段拆分（性能核心）**

竞价时 `currentPrice / bidCount / endTime / currentWinnerId` 会被高频写入。若与拍品描述、图片数组放在同一文档，每次出价都要重写整个文档，写入放大严重。

```
t_item            物品静态信息（标题、描述、图片、分类、成色）→ 几乎不写
t_auction         拍卖规则 + 状态（起拍价、加价幅度、起止时间）→ 低频写
t_auction_live    竞价热点（currentPrice、bidCount、endTime、winnerId、version）→ 高频写
```

出价只写 `t_auction_live`，文档极小，并发更新性能显著提升。**这个设计本身就能写进论文，是一个有说服力的优化点。**

**② 出价用 version 条件更新（保证不错价）**

```js
// cloudfunctions/bid/index.js（节选，需 wx-server-sdk）
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()
const _ = db.command

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext()
  const { auctionId, price } = event
  const liveCol = db.collection('t_auction_live')

  // 最多重试 3 次，失败即返回"价格已变动"
  for (let i = 0; i < 3; i++) {
    const live = (await liveCol.doc(auctionId).get()).data
    if (live.status !== 'ONGOING') return { code: 3001, msg: '拍卖已结束' }
    if (live.winnerId === OPENID) return { code: 3002, msg: '您已是最高出价者' }
    if (price < live.currentPrice + live.increment) {
      return { code: 3003, msg: `最低出价 ${live.currentPrice + live.increment} 分` }
    }

    // 条件更新：version 未变才写入，原子操作
    const res = await liveCol.where({
      _id: auctionId,
      version: live.version,
      status: 'ONGOING',
      currentPrice: _.lt(price)
    }).update({
      data: {
        currentPrice: price,
        winnerId: OPENID,
        bidCount: _.inc(1),
        version: _.inc(1),
        lastBidAt: new Date()
      }
    })

    if (res.stats.updated === 1) {
      // 抢价成功：写流水 + 防狙击判定
      await db.collection('t_bid_record').add({
        data: { auctionId, userId: OPENID, price, bidTime: new Date(), status: 'LEADING' }
      })
      return await handleAntiSniping(auctionId, live)
    }
    // updated === 0：被别人抢先，循环重试
  }
  return { code: 3004, msg: '当前出价激烈，请重新出价' }
}
```

**要点**：`where` 里的 `version` + `currentPrice: _.lt(price)` 双条件，配合 `stats.updated` 判定，等价于 MySQL 的乐观锁。**这段代码是答辩时证明"云开发也能保证并发正确性"的核心证据，务必讲清。**

**③ 防狙击（逻辑与 Spring Boot 版完全一致）**

```js
async function handleAntiSniping(auctionId, live) {
  const now = Date.now()
  const endTs = new Date(live.endTime).getTime()
  const remain = endTs - now
  if (remain <= 5 * 60 * 1000 && live.extendCount < 3) {
    await db.collection('t_auction_live').doc(auctionId).update({
      data: { endTime: new Date(now + 2 * 60 * 1000), extendCount: _.inc(1) }
    })
    return { code: 0, data: { extended: true, endTime: now + 120000 } }
  }
  return { code: 0, data: { extended: false } }
}
```

```json
}
```

> cron 段数与取值格式请以[云函数定时触发器文档](https://developers.weixin.qq.com/miniprogram/dev/wxcloud/guide/functions/triggers.html)为准，此处仅示意"每分钟执行"。

幂等靠两点：① 先用 `where({status:'ONGOING', endTime: _.lte(now)}).update({status:'SETTLING'})` 抢占状态，`stats.updated === 1` 才处理；② `t_order` 的 `auctionId` 建**唯一索引**（云开发控制台手动创建）兜底。**唯一索引这一步必须截图进论文，是很实的工程细节。**

**⑤ 数据库安全规则（必配，否则出价能被前端伪造）**

```json
// t_auction_live 权限：所有用户可读，仅云函数（管理端）可写
{ "read": true, "write": false }
```

前端**只能通过云函数出价**，绝不能 `wx.cloud.database().collection('t_auction_live').update(...)` 直写——那样任何人都能改价格。这一点是云开发项目最常见的安全事故，答辩若被问到必须答得出。

**⑥ AI 密钥**

配在云函数的环境变量里（控制台 → 云函数 → 配置 → 环境变量），代码用 `process.env.AI_API_KEY` 读取，**不写进代码、不进 Git**。

### B.3 论文写法调整（保住"设计"章节）

云开发下不要写"三层架构"，改写**四层逻辑架构**，层次并不少：

```
表现层    小程序 WXML/WXSS + Vue 管理后台
接入层    云函数网关（鉴权、参数校验、统一响应、限流）
服务层    业务服务（拍卖、竞价、结算、账户、AI）
数据层    云数据库（14 集合）+ 云存储（图片）
```

再把 B.2 的四个设计（热点字段拆分、version 条件更新、触发器幂等结算、安全规则）各写一小节，第 4 章"系统设计"照样够篇幅。**真正少的不是层次，是"服务器部署与运维"这一块**——用"云原生部署架构"替代即可。

### B.4 云开发方案的代价清单（写进论文"不足与展望"）

| 代价 | 影响 | 论文中的表述方向 |
|---|---|---|
| 无 Redis 层 | 单场拍卖并发上限低于 Spring Boot 方案 | 可作为"后续引入 Redis 缓存层"的展望 |
| 冷启动 | 云函数首次调用延迟 200ms-1s | 说明已用预热/常驻配置缓解 |
| 文档型数据库 | 无 JOIN，多表关联需应用层拼装或冗余字段 | 说明已用冗余字段（如拍品的卖家昵称）换查询性能 |
| 绑定微信生态 | 无法迁移到其他平台 | 承认平台绑定，说明校园场景下可接受 |
| 免费额度 | 超出需付费，演示够用 | 说明配额评估 |

### B.5 什么情况下必须换回 Spring Boot

命中任意一条，就别选云开发：

- 导师/学院明确要求"B/S 三层架构""独立服务端""部署到服务器"
- 开题报告已写死 Spring Boot / Java 技术路线（改了要重新审批，不划算）
- 目标是评优秀毕设（评委对"技术难度"权重高）
- 想顺便把项目当求职作品（云开发经历在企业端认可度低）

**反之，如果只是想稳过、把时间留给论文和 AI 创新点，云开发是完全站得住的选择。**
