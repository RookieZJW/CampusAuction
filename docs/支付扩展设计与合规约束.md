# 支付扩展设计与合规约束 — 校园在线拍卖系统

> 2026-11-21 定稿。对应需求：「关于拍卖的交易，应该怎么做？只能使用虚拟货币吗？我想使用微信支付的功能，应该怎么做？有没有什么比较好的方案？」
> 结论：**实现方案 B —— 可插拔支付网关 + 模拟支付**。本文既是开发说明，也是论文「支付模块设计」与答辩问答的底稿。

---

## 一、先厘清一个误区：当前不是「只能用虚拟货币」

项目里存在 `t_user.balance` 和 `t_account_log`，很容易被理解成「虚拟货币支付」。但通读交易链路后可以确认：

| 环节 | 现状 | 是否涉及真实资金 |
|---|---|---|
| 出价 | 冻结 10 元虚拟保证金（单位：分，`int`） | 否，纯记账 |
| 成交 | 结算任务生成 `t_order`，状态 `PENDING_TRADING` | 否 |
| 支付 | **无任何支付代码**（无充值、无收款、无 `wx.requestPayment`） | 否 |
| 交割 | 买卖双方线下约定地点，买方点「确认交割完成」 | 否 |
| 完成 | 解冻买方保证金、双方信用分 +2 | 否，纯记账 |
| 违约 | 待交割 48 小时未完成 → 订单取消 + 没收冻结保证金 + 信用分 -10 | 否，纯记账 |

也就是说，`balance` 是**保证金风控额度**，不是钱包余额；`t_order` 是**履约状态机**，不是支付单。系统从头到尾没有真实资金链路，所以问题不是「能不能换一种货币」，而是「要不要引入一条资金链路、以什么形态引入」。

## 二、四种候选方案与取舍

| 方案 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| A 虚拟记账 + 线下交割 | 维持现状，论文里如实说明 | 零改动、零风险 | 用户明确想看到微信支付，答辩说服力弱 |
| **B 可插拔支付网关 + 模拟支付** | 抽象 `PaymentProvider`，默认 `MockPaymentProvider`，前端仿微信收银台 | **答辩可完整演示资金链路；代码结构面向未来；零合规风险** | 不是真实扣款，需在演示与论文中明确标注 |
| C 直连微信支付（平台代收） | 申请商户号，买家付款到平台商户号，平台再结算给卖家 | 技术上最直接 | **二清风险 + 主体不符**，见下节 |
| D 电商收付通合规上线 | 卖家作为二级商户进件，资金直达卖家侧 | 真正合规上线 | 需企业主体、拍卖资质、公网服务器、HTTPS 回调、对账退款，远超毕业设计范围 |

选 B 的理由：它把「资金链路」这一层**做成接口**而不是做进业务代码，既能当场演示，又能在论文里给出清晰的合规边界与演进路线，是毕业设计最合适的落点。

## 三、为什么不能直接接微信支付（合规约束）

这一节是答辩最容易被追问的地方，务必按原文口径回答。

### 3.1 微信支付本身可以接，但只是「技术门槛」

- 已认证小程序 + 个体工商户主体（`中牟县赤威科技工作室`）**可以**申请微信支付商户号。
- 需要：营业执照、法人身份证、结算银行账户、商户号与 AppID 绑定；费率通常 0.6%–1%，审核约 1–2 个工作日。
- 技术还需要：公网服务器、HTTPS 回调地址、APIv3 密钥、商户私钥与证书序列号、平台证书验签、回调幂等、退款与对账。

### 3.2 真正的拦路虎是「拍卖类目」与「二清」

1. **经营性网络拍卖资质**：经营性网络拍卖通常要求企业法人资格与《拍卖经营批准证书》，文物拍卖还需《文物拍卖许可证》。个体工商户主体不适合正式上线拍卖类目。
2. **二清风险（核心）**：本项目是 C2C 多卖家平台。若「买家付款到平台商户号 → 平台再结算给卖家」，平台既归集了货款又做了二次清算，属于无证二清。资金一旦过平台账户，性质就变了。
3. **正确形态**：微信支付「电商收付通」/服务商模式 —— 卖家作为**二级商户**单独进件，买家资金直接进入/冻结在卖家侧，平台只发送分账、解冻指令，**不触碰货款**。这需要平台侧有服务商资质与完整的进件、对账、退款体系。

> 一句话答法：**「技术上能接，合规上不能这么接。个体工商户主体 + 平台代收代付同时踩了拍卖类目资质和二清两条线，所以本设计用可插拔网关把资金链路抽象出来，演示用模拟支付，正式上线走电商收付通。」**

## 四、方案 B 架构设计

### 4.1 分层

```
小程序  cashier（仿微信收银台）
   │  POST /orders/{id}/pay          发起支付
   │  POST /orders/{id}/pay/confirm  模拟支付成功
   │  POST /orders/{id}/pay/close    关闭支付单
   ▼
OrderController ──► PaymentService（编排：状态机 / 幂等 / 通知）
                        │
                        ▼
                  PaymentProvider（接口）
                   ├─ MockPaymentProvider   ← 默认装配，演示用
                   └─ WxPayProvider        ← 预留骨架，默认不装配
                        ▲
PayNotifyController ────┘  统一回调 /api/v1/pay/notify/{provider}
```

切换方式只有一行配置：`payment.provider: mock | wxpay`（`@ConditionalOnProperty`）。订单状态机、回调幂等、前端收银台都不用改。

### 4.2 两个状态机解耦（关键设计）

`t_order` 上现在有**两个互不覆盖的维度**：

- `status`：履约 —— `PENDING_TRADING` / `COMPLETED` / `CANCELLED`
- `pay_status`：资金 —— `UNPAID` / `PAYING` / `PAID` / `CLOSED`

这样做的好处：现有「虚拟保证金 + 线下交割」链路完全不用改，答辩时即使不支付也能走完线下交割；将来要强制「先付后交割」，只需把 `payment.require-before-complete` 改成 `true`（`OrderServiceImpl.completeTrade()` 里已有该校验，默认关闭）。

资金状态流转：

```
UNPAID ──发起支付──► PAYING ──回调/确认──► PAID
   ▲                   │
   └──── 关闭支付单 ────┘ (CLOSED 可重新发起，生成新 pay_no)
```

### 4.3 幂等与一致性

| 风险 | 处理 |
|---|---|
| 重复发起支付 | `PAYING` 且有 `pay_no` 时幂等返回已有支付单，不重复生成单号 |
| 并发重复回调 | CAS 更新 `WHERE pay_status = 'PAYING'`，更新行数为 0 时重查；已 `PAID` 直接幂等成功 |
| 伪造/错渠道回调 | `resolveProvider()` 校验渠道标识与当前启用网关一致；`verifyNotify()` 验签（模拟渠道校验单号非空，真实渠道为 APIv3 平台证书验签 + 报文解密） |
| 单号冲突 | `t_order.uk_pay_no` 唯一索引兜底 |
| 污染保证金账 | **模拟支付不写 `t_account_log`、不改 `t_user.balance`**，只更新支付维度字段并通知双方 |

`confirm`（演示专用）刻意**复用同一条 `handleNotify()` 回调链路**，而不是另写一段状态更新逻辑 —— 这样答辩现场跑的「验签 → 幂等 → CAS」就是真实上线时跑的那段代码。

## 五、数据库改动

`sql/init.sql` / `sql/migration/2026-11-21-payment-gateway.sql` / `server/src/main/resources/schema.sql` 三处同步，后者随 `spring.sql.init.mode=always` 启动自动幂等执行。

```sql
pay_status     VARCHAR(20) NOT NULL DEFAULT 'UNPAID'  -- UNPAID/PAYING/PAID/CLOSED
pay_no         VARCHAR(64) NULL                        -- 支付单号 PAY+时间戳+随机
pay_provider   VARCHAR(20) NULL                        -- MOCK / WXPAY
pay_amount     INT         NULL                        -- 本次支付金额（分）
transaction_id VARCHAR(64) NULL                        -- 第三方交易号
paid_at        DATETIME    NULL                        -- 支付成功时间
UNIQUE KEY uk_pay_no (pay_no)
```

存量订单默认 `UNPAID`，历史演示数据不受影响。新订单在 `SettleServiceImpl.settle()` 建单时显式写入 `pay_status = UNPAID`。

## 六、接口清单

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/api/v1/orders/{id}/pay` | 发起支付，返回收银台参数 | 买方 |
| GET | `/api/v1/orders/{id}/pay` | 查询支付状态 | 买卖双方 |
| POST | `/api/v1/orders/{id}/pay/confirm` | 模拟支付成功（演示专用，复用回调链路） | 买方 |
| POST | `/api/v1/orders/{id}/pay/close` | 关闭支付单，可重新发起 | 买方 |
| POST | `/api/v1/pay/notify/{provider}` | 统一回调（白名单，验签保证合法性） | 无登录态 |
| GET | `/api/v1/orders/mine` | 订单列表，已返回 `payStatus/payNo/transactionId/paidAt/payProvider` | 登录 |

微信支付 v3 要求回调应答为 HTTP 200 + `{"code":"SUCCESS"}`，故 `PayNotifyController` 不套项目统一 `Result` 包装；失败返回 `{"code":"FAIL"}`。

新增错误码：`3012` 当前订单状态不允许支付、`3013` 支付状态已变更、`3014` 支付网关未启用或回调验签失败。

## 八、答辩问答底稿

**Q：为什么不用真实微信支付？**
A：主体是个体工商户，且拍卖是 C2C 多卖家。平台代收货款再结算给卖家属于二清，经营性网络拍卖还要求企业法人和《拍卖经营批准证书》。技术上能接，合规上不能这么接。所以本设计把支付抽象成 `PaymentProvider` 接口，默认装配模拟支付完成演示，正式上线切换为电商收付通模式，卖家作为二级商户进件，资金不经过平台。

**Q：模拟支付和真实支付的代码差异有多大？**
A：订单状态机、回调幂等、CAS 流转、前端收银台是共用的。差异集中在 `PaymentProvider` 的两个方法：`prepare()` 真实渠道要调 JSAPI 统一下单并生成 `paySign`，`verifyNotify()` 要做 APIv3 平台证书验签与报文解密。`WxPayProvider` 里已按顺序列出 TODO，切换只需改一行配置。

**Q：支付会不会影响虚拟保证金？**
A：不会。支付状态与履约状态是 `t_order` 上两个独立字段；模拟支付不写 `t_account_log`、不改 `balance`，保证金仍在「确认交割完成」时解冻、违约时没收，原有风控逻辑零改动。

**Q：重复点支付、重复回调会怎样？**
A：三层保护 —— `PAYING` 状态幂等返回已有支付单、`uk_pay_no` 唯一索引、CAS 更新 `WHERE pay_status='PAYING'`。重复回调直接返回成功，不重复通知、不重复记账。

**Q：能否强制先付款再交割？**
A：可以，`payment.require-before-complete=true` 即开启。默认 false 是为了保留线下面交的完整演示链路，也符合校园二手交易「当面验货」的真实场景。

## 九、正式上线演进路线

1. 主体升级为公司主体，取得经营性网络拍卖所需资质；
2. 申请微信支付服务商/电商收付通能力，卖家作为二级商户进件；
3. 部署公网服务器、HTTPS 回调、APIv3 证书与平台证书轮换；
4. 启用 `WxPayProvider`，补齐 `prepare()` 的 JSAPI 下单与 `verifyNotify()` 的验签解密；
5. 补支付流水表与对账、退款、分账/解冻指令、异常补单；
6. 前端把自绘收银台换成 `wx.requestPayment`，保留本项目收银台作为降级/预览；
7. 打开 `payment.require-before-complete`，做全链路压测与资金对账。

> 边界声明：本项目的 `MockPaymentProvider` **仅用于教学与答辩演示**，不产生任何真实资金变动，不得用于实际经营收款。
